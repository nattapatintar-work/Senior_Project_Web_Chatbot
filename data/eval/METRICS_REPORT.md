## 1. How to read these numbers

Definitions come from `tools/eval_rule_score.py` (line numbers are for that file).

| term | meaning | where |
|---|---|---|
| item total | A + B + C for one returned recipe | `score_recipe` `:105-120` |
| A | 2 if a user ingredient is a MAIN ingredient, 1 if only an OPTIONAL one, else 0 | `points_a` `:80-86` |
| B | 2 if no main ingredient is missing, 1 if the missing share of mains is <= 0.5, else 0 | `points_b` `:89-98` |
| C | 0 if `category == "dessert"`, else 1 (snack, drink, condiment and savory all get 1) | `points_c` `:101-102` |
| lenient / strict | an item passes if its total is >= 3 / >= 4 | `:54-55` |
| P@3 | passing items / items returned, per query, then the mean over queries. Queries that returned nothing are skipped | `query_metrics` `:161`, `aggregate` `:196` |
| Hit@3 | 1 if at least one item passes, else 0. Every query counts; an empty result is a miss | `query_metrics` `:162`, `aggregate` `:197` |
| mean total | mean of the item totals of the chosen variant, per query, then over queries | `query_metrics` `:156`, `aggregate` `:193` |
| coverage | distinct recipes returned / catalog size | `aggregate` `:206` |
| dessert share | dessert items / returned items (pooled, and mean per query) | `query_metrics` `:174`, `aggregate` `:209-210` |
| diversity | mean pairwise Jaccard distance of main + optional ingredient sets within one top-3 | `diversity` `:137-142` |
| system violations | returned items whose health tag or hard-excluded ingredient breaks the system's own filter | `violations` `:67-77`, count at `:253` |

### The three variants

Each variant is the same A + B + C total with a different cap or violation rule (`score_recipe` `:105-120`).

| variant | what it does |
|---|---|
| `total_capped` | 0 if `violation_with_optional` (an excluded ingredient anywhere, optional included, or a tag problem); otherwise A+B+C, and a dessert's total is capped at 2 |
| `total_uncapped` | 0 if `violation_with_optional`; otherwise A+B+C, never capped |
| `total_system_violation_only` | like `total_capped`, but zeroed only by `violation_system_rule` (excluded ingredient in main or seasonings, or a tag problem), which is what `recommend()` itself enforces (`recommender/recommend.py:162-169`) |

### What capped and uncapped answer

- **Capped** answers: *are the returned items non-dessert, and do they match the user's ingredients?* It applies to every returned dessert whatever the query was about: `points_c` takes no query input, so a dessert-oriented query is penalised the same way.
- **Uncapped** answers: *how well do the returned items overlap the user's ingredients (A, B), with one point less for a dessert (C)?* It is the better available proxy for ingredient match, but it is not pure match quality: C still costs a dessert one point and a violation still zeroes an item.
- **Why a capped dessert can never pass:** `DESSERT_TOTAL_CAP = 2` is below both pass lines (lenient >= 3, strict >= 4). Any dessert has C = 0 and its total is cut to at most 2, so it fails capped lenient and capped strict whatever its ingredient match. Uncapped, a dessert can reach 4 (A 2 + B 2 + C 0), so it can pass both lines.
- Consequence: a low capped number for a dessert-heavy group describes the rubric's cap, not the recommender's matching.

## 5. Known limitations of this evaluation

1. **Rubric constants are self-defined.** Every constant (A, B, C points, `B_PARTIAL_SHARE`, `DESSERT_TOTAL_CAP`, both pass lines, `TOP_K`) is commented "definition we chose" in `tools/eval_rule_score.py:44-56`; none is derived from data. The stored `constants` block says the same.
2. **Draft test set, no human gold set.** `data/eval/test_set_draft_v1.json` has 30 queries. Its `preview_top3` field came from an external simulation and is ignored. No human relevance labels exist, so the rubric measures ingredient overlap, not whether a dish is a good answer.
3. **Category picker and seasoning weight are not exercised.** The stored call is `recommend(ingredients=used_ingredients, health_tags, excluded, top_k=3, seasonings=[])`: no `category` argument (default `all`) and `seasonings_ticked` = []. So the category choice and `SEASONING_WEIGHT` have no effect on these numbers.
4. **Snack and drink escape the dessert penalty** (`points_c` `:101-102` gives them C = 1, and the cap only applies when C = 0). In the stored top-3 file the returned categories are {'dessert': 19, 'savory': 70}: no snack, drink or condiment was returned, so this has no effect on the stored numbers. It would matter if the test set were extended.
5. **Violation rule mismatch.** `recommend()` drops a dish only for an excluded ingredient in main or seasonings (`recommender/recommend.py:162-169`), but the capped and uncapped variants zero any item with the excluded ingredient even only in optional (`violation_with_optional`, `tools/eval_rule_score.py:76`). The stored `differing_violations` lists 2 such returned item(s): D2 rank 3 recipe th_170; E6 rank 2 recipe th_293. They score 0 in `total_capped` and `total_uncapped`, but not in `total_system_violation_only`.
6. **No LLM-as-judge result exists.** The rubric is deterministic code only. `tools/eval_rule_score.py` describes itself as the deterministic half, and no judged half exists in the repo.

## 6. How to quote these numbers

- Always give the variant **and** the pass line, for example "total_uncapped, lenient, P@3 0.967". Never write just "P@3".
- Never describe a capped P@3 as match quality. For ingredient match quote `total_uncapped`; for "dessert items do not pass" quote `total_capped` and say that the cap forces it.
- Never quote a capped lenient or strict figure for a group that mostly returns desserts (Group E) without the uncapped figure next to it.
- Say these are self-defined rubric scores on a 30-query draft set with no human labels, not accuracy or user satisfaction.
- Cite the stored file (`data/eval/post_relabel_rule_metrics.json`) and the commit, and do not mix the old (`db8c153`) and new numbers without saying which is which.
