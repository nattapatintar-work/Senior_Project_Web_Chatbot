### `data/ingredients.json` — 127 entries, the class-lock re-confirmed at 100

Person 1 retrained YOLO on 100 classes (up from 20) and this was verified against their
notebook this session. The dictionary now has:
- **100 detectable entries**, `yolo_class_id` 0-99, in a completely different order than the
  old locked 20 (e.g. `egg` moved from id 1 to id 5)
- **27 text-only entries** (22 seasonings + 5 carb staples: `rice`, `rice_noodle`,
  `glass_noodle`, `egg_noodle`, `spaghetti`)
- New `category` field (protein / herb_aromatic / vegetable / mushroom / carb / fruit /
  nut_seed / seasoning) and `confusable_with` field (flags visually/name-similar pairs like
  `eggplant`/`thai_eggplant`)
- `is_animal_product` corrected on the 5 curry pastes and `chili_paste` — they contain
  shrimp paste, so they must exclude vegan. Checked every recipe using any of them: all
  already carried `fish_sauce` independently and were already `excluded_for: vegan`, so this
  correction flipped no recipe's tags

**A real bug found and fixed:** `หมูสับ` (minced pork) was listed as a synonym under both
`pork` and `minced_meat`, which crashed `test_no_synonym_is_shared_by_two_ingredients`
outright. Fixed by removing it from `pork`'s list — `หมูสับ` literally means *minced* pork,
so `minced_meat` is the correct match, not the more general `pork`.

**Three keys intentionally not re-added** despite the old `recipes.json` needing them:
`dried_shrimp`, `bean_sprout` (distinct from `soybean_sprouts`), and a generic `mushroom`
catch-all. This was an explicit decision (confirmed with the user) — dishes needing them
(`ส้มตำไทย`, `ผัดไทยกุ้ง`) were dropped rather than the dictionary being widened again.

### `data/recipes.json` — 40 -> 84, every recipe carries `recipe_source_url` now

Rebuilt in two parts:

1. **38 of the original 40 carried forward.** 8 stale ingredient keys renamed
   (`thai_basil`→`basil`, `peanut`→`peanuts`, `long_bean`→`yardlong_bean`, `mint`→
   `mint_leaves`, `chinese_broccoli`→`chinese_kale`, generic `mushroom`→`straw_mushroom` in
   the 3 tom-yum-style dishes that only used it for flavor, not species-specificity). 2
   dropped (`ส้มตำไทย`, `ผัดไทยกุ้ง` — needed the retired `dried_shrimp`/`bean_sprout`
   keys).
2. **46 new recipes**, built to deliberately maximize ingredient coverage — picking dishes
   that use ingredients nothing else in the database touched. Sourced via `tools/thaifcd.py`
   (real Thai FCD lookups, ~120 food records now cached, all fetched live this session) and
   real web searches for `recipe_source_url` (no URL was written without being actually
   fetched).

Result: **31 direct / 53 computed**, **74 of 84 photo-reachable**, **117 of 127 ingredients**
used by at least one recipe. The 10 still unused (`spaghetti`, `hyacinth_bean`, `chayote`,
`amaranth`, `asparagus`, `bottle_gourd`, `green_peas`, `clove_basil`, `rambutan`, `tamarind`)
split into two kinds: 3 have no usable Thai FCD nutrition record at all (`spaghetti` — no
plain-pasta entry; `hyacinth_bean` — no entry; `chayote` — only a null-macro leaf-shoot
record), the other 7 simply didn't fit a dish built this session and remain open coverage
gaps, not data gaps.

Every recipe now also carries **`recipe_source_url`**, a new required field (enforced by a
new test) separate from `nutrition_source` — the former cites where the dish's ingredient
list came from, the latter always cites Thai FCD (or Thai FCD + a declared exception, as
before with the broccoli/USDA case).

### Test fixes forced by the above (all real bugs, not busywork)

- `tests/test_recipes.py`'s hardcoded `flesh` set (used to derive the vegetarian-exclusion
  rule) **crashed outright** — it hardcoded `dried_shrimp`, which no longer exists in the

- 3 of my own new recipes had self-contradicting health tags (tagged `keto` or `clean`

- `tests/test_recommend.py::test_have_is_the_intersection_of_user_ingredients_and_the_dish`

  breaks (two dishes that actually contain both queried ingredients now outrank it). Fixed
  by widening `top_k` so the test checks its actual intent (the have/missing intersection
  logic) rather than ranking position.
- `data/recommender_dev_set.json`'s 8 cases needed re-deriving after renumbering: 2 were

  dishes, so the pork-exclusion check they claimed to run was vacuous. All 8 re-verified

## 4. Issues Found and Fixed

**1. `หมูสับ` synonym collision in `ingredients.json`.** See §2 — a real dictionary bug that
crashed a contract test, not something introduced by this session's own edits (it was
already present in the dictionary handed off at the start of the session).

**2. Three self-authored health-tag bugs.** Wrote `keto`/`clean` tags on 3 new recipes
without checking them against the recipe's own numbers first — exactly the kind of error
`tests/test_recipes.py` exists to catch (per its own docstring: "forty recipes entered by
hand ... is exactly the situation where a typo survives"). All three caught by the suite on
the first full run, none shipped silently.

**3. `run_recommender_dev_set.py` passing for the wrong reason.** Not a crash, so it would
never have surfaced without deliberately re-running it — 2 of 8 cases' negative assertions
had drifted to check IDs that no longer meant what the test claimed. Worth naming
explicitly: **a green non-pytest dev script is not the same guarantee as a green pytest
suite**, since nothing forces it to run automatically.

**4. Windows Python does not understand `/c/...`-style paths from Bash.** Tried to write a
scratch file to the session's scratchpad directory using the Bash-tool's Unix-style path;
`os.path.exists` returned `False` from Python even though `ls` could see the directory.
Fixed by using the native `C:\Users\...` form, or by just writing into the project directory
and cleaning up after. Worth remembering for any future Python-from-Bash scratch work on
this machine.
