### `extract()`'s real pipeline

1. Tokenize with `pythainlp.word_tokenize()`, passing a `pythainlp.util.Trie` built from
   every synonym in both dictionaries as `custom_dict`.
2. Walk tokens; each one tries an exact match against the synonym index, then a rapidfuzz
   fallback (cutoff 85, minimum token length 4) if that fails.
3. A negation cue ("ไม่" + "เอา"/"ใส่"/"มี") flips everything matched until the next
   whitespace-delimited segment from `ingredients` to `excluded`.
4. Anything in `excluded` is removed from `ingredients` — a key is never in both.

Frozen contract honored: same three keys, same types, verified by both
`tests/test_contract.py` (shape, now exercised against real logic for the first time) and
`tests/test_extract.py` (content).

### The finding that reshaped the fix: tokenization, not sort order

C4 (raised Week 1, restated Week 3 and session 5) diagnosed the bug as a matching-order
problem and prescribed "sort synonyms by length descending." That fix cannot work, and
this session found out why directly rather than assuming the old diagnosis was right:

```
word_tokenize("ไม่เอาน้ำมันหอย")          # no custom dict
    -> ['ไม่', 'เอา', 'น้ำมัน', 'หอย']
```

PyThaiNLP's *default* tokenizer splits "น้ำมันหอย" (oyster sauce) into "น้ำมัน" (oil) +
"หอย" (not a dictionary key) **before any synonym list is ever consulted.** No sort order
downstream can recover a compound that's already gone. Same story for the project's own
canonical worked example — "คลีน" (clean) splits into "คลี" + "น" by default, so
`Claude.md:122`'s sentence would silently fail to detect its own health tag.

**Fix, verified live:** a `pythainlp.util.Trie` built from all 306 ingredient synonyms
plus the health-term vocabulary, passed as `custom_dict`. Confirmed before/after —
"น้ำมันหอย" and "คลีน" both survive as single tokens; nothing already-correct
("พริกไทย", "กุ้งแห้ง", "น้ำปลา") was disturbed.

### Full collision audit: 56 pairs, not 11

C4's tables listed 11 collision pairs. A full audit of all 306 synonyms this session found
**56** — including 18 English pairs C4 never considered (`egg`/`eggplant`,
`fish`/`fish sauce`, `onion`/`green onion`, …) and several more Thai pairs from curry-paste
synonyms added while writing `recipes.json` (`พริกแกงเขียวหวาน`/`พริก`,
`พริกแกงกะหรี่`/`พริก`, …). All resolve correctly under the tokenizer fix. Representative
cases are pinned in `tests/test_extract.py::COLLISION_CASES`.

**Four of C4's original 11 were not real collisions.** `มะเขือ-`, `ถั่ว-`,
`มันฝรั่ง`/`มันเทศ`, `หอมใหญ่`/`ต้นหอม` are sibling prefixes — neither is a substring of
the other, since no bare `มะเขือ`/`ถั่ว`/`มัน`/`หอม` synonym exists. Longest-match was never
going to break on these. They're a *fuzzy*-matching risk instead (a loose cutoff could
conflate look-alikes), and now have their own test category, `SIBLING_CASES`.

### Health-tag vocabulary: created from scratch

`ingredients.json` had zero health-tag words in it, and `HEALTH_TAGS.md` only defines the
four tags as recipe-side rules ("carb ≤ 10g"), never as things a user types. Session
decision (confirmed with you): เจ maps to `vegan`, accepted only inside the real compound
phrases `กินเจ`/`อาหารเจ` — never a bare `เจ` synonym, since `เจ` alone is a substring of
`เจอ` ("to meet") and `เจ็ด` ("seven") and would false-positive on unrelated sentences.
Verified: `word_tokenize("เจอกันพรุ่งนี้")` (see you tomorrow — no food content) never
isolates a bare `เจ` token, with or without the custom dict, and
`tests/test_extract.py::test_je_maps_to_vegan_only_inside_the_real_phrase` pins this.

### Documented limitation: Thai typo recovery mostly doesn't work

English typos recover reliably — `"chiken"` scores 92% against `"chicken"`. Thai typos
mostly don't, verified directly: a misspelled Thai word is rarely in the custom
dictionary, so the tokenizer shatters it into syllable fragments before rapidfuzz ever
sees it:

```
word_tokenize("มีมะเขือเทดด้วย")   # typo of มะเขือเทศ, tomato
    -> ['มี', 'มะเขือ', 'เท', 'ด', 'ด้วย']
```

The surviving `มะเขือ` fragment scores only 80% against the correct synonym — below the
85 cutoff. A looser cutoff was tried and rejected during design: at 60%, unrelated short
tokens started matching real synonyms by accident (`กระ` → `กระเพรา` at 60%). This is now
a tested boundary, not a silent gap —
`test_thai_typo_recovery_is_a_known_gap_not_a_silent_wrong_answer` asserts the failure
mode is *nothing matched*, never *the wrong thing matched*.
