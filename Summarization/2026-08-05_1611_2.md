### ⚠️ The most important stack fact: line-bot-sdk v3, not v2

`requirements.txt` pins `line-bot-sdk>=3.11.0`, and 3.25.0 is installed. **Nearly every
LINE bot tutorial online is written for v2, and v2 code does not run on v3.**

| | v2 (most tutorials) | v3 (what we use) |
|---|---|---|
| import | `from linebot import LineBotApi` | `from linebot.v3.messaging import MessagingApi` |
| incoming text | `TextMessage` | `TextMessageContent` |
| outgoing text | `TextSendMessage` | `TextMessage` |
| reply | `line_bot_api.reply_message(tok, msg)` | `MessagingApi(client).reply_message(ReplyMessageRequest(...))` |

Note the cruel detail: `TextMessage` exists in **both**, meaning different things. If a
copied snippet raises `ImportError` or a confusing type error, this is why. Use
<https://github.com/line/line-bot-sdk-python>, not blog posts.

### `api/session.py` — the core of Week 2

Solves a real problem: people send a photo, then a caption two seconds later. Without
buffering that is two webhooks, so the bot replies twice, and neither reply has the whole
picture.

Debounce: buffer the message, start a 2.5s timer, and restart that timer on every new
message. Work runs only after the user has been quiet.

Three details that took the most care:

1. **The newest reply token wins.** Every event carries its own token, single-use, ~30s
   life. Merging three messages means only one reply, so the freshest token is kept — it
   has the most life left when the timer fires.
2. **The flush pops the session while holding the lock**, then does slow work *after*
   releasing it. Popping under the lock gives the thread sole ownership so a
   simultaneously-arriving message starts a clean session; releasing before the slow work
   stops one user's downloads freezing everyone else's.
3. **No imports from `api/config.py` or `api/main.py`.** config crashes without a `.env`,
   which would make the tests un-runnable; importing main would be circular. Settings and
   the worker are injected via `configure()` and `set_flush_handler()`.

### `api/main.py` — how "verify signature" and "reply in 200ms" coexist

These look contradictory: `handler.handle()` dispatches to `@handler.add` callbacks
**synchronously**, so the HTTP response waits on them. LINE retries a slow webhook, which
would make the bot reply twice.

Resolution: the callbacks **only buffer** — a dict write, microseconds. All real work
happens later on the timer thread. The debounce requirement and the answer-fast
requirement turn out to be satisfied by the same mechanism.

Measured: **2–21ms** per webhook.

## 4. Issues Found and Fixed

**1. `print()` output vanished when redirected to a file.**
Python block-buffers stdout when it is not a terminal, so diagnostics sat unwritten while
the server ran, and were lost entirely when it was killed. This nearly caused a false
conclusion that the debounce timer had never fired. Fixed with
`sys.stdout.reconfigure(line_buffering=True)` at startup plus `flush=True` on the four
diagnostic prints. Matters because the log is the only window into the timer thread.

**2. A false 2-second latency reading.**
The first webhook timing test reported ~2000ms. The cause was the *test client* resolving
`localhost` to IPv6 first and waiting for it to fail; against `127.0.0.1` the same request
took 2ms. Worth remembering during Week 8–10 testing: **use `127.0.0.1`, not `localhost`**,
or you will chase phantom latency.

**3. (carried) cp874 `UnicodeEncodeError`.** Still relevant — the first PyThaiNLP output
appeared as mojibake, which looked like a library problem but was the console codepage.
An encoding-looking failure on this project is usually the terminal, not the library.
